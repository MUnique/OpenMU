# Loading of the game configuration

The `GameConfigurationLoader` loads the game configurations with one `select` statement per
table. The statements are sent to the database as one batch. The rows are materialized and
the objects are connected by generated code.

It creates the same object graph as the `GameConfigurationJsonObjectLoader`, which loads the
configuration with one large json query (see `../Json`), but the database doesn't need to
build the json, and the client doesn't need to parse it:

* The tables of the configuration schema are loaded completely. The tables of other schemas,
  e.g. the items of the merchant stores, are filtered by the objects which reference them.
* The same entity types are loaded, which are reached from the game configuration through the
  navigations which are members of the aggregate, like the json query does it.
* The same properties are set, which are determined by the same rules as the
  `ReferenceResolvingConverter` uses for the properties of the json objects.

The order of the items of many-to-many collections may differ from the json query, because
it's not defined by both. The json query returns them in the order of the query plan.

The json query can still be used by setting the `AppContext` switch
`MUnique.OpenMU.Persistence.DisableGameConfigurationLoader`.

## When to generate the code again

Whenever the model changes, i.e. when the data model or the `OnModelCreating` methods of the
contexts change - usually together with a migration and the compiled models
(see `../CompiledModels/Readme.md`).

The test `GameConfigurationLoaderGeneratorTest` in `tests/MUnique.OpenMU.Tests` fails when the
generated code doesn't match the model.

## How to generate it

The code is generated by the `GameConfigurationLoaderGenerator` of the project
`MUnique.OpenMU.Persistence.EntityFramework.DesignTime`. Run the test with the environment
variable `OPENMU_UPDATE_GENERATED_CODE` set to `1`, in the root folder of the repository:

```
OPENMU_UPDATE_GENERATED_CODE=1 dotnet test tests/MUnique.OpenMU.Tests --filter FullyQualifiedName~GameConfigurationLoaderGeneratorTest
```

It overwrites `GameConfigurationLoader.Generated.cs`.

If the project doesn't compile anymore because of the model change, replace the content of
`GameConfigurationLoader.Generated.cs` by the following stub first:

```csharp
// <auto-generated />
#nullable enable

namespace MUnique.OpenMU.Persistence.EntityFramework.Loading;

internal sealed partial class GameConfigurationLoader
{
    private static readonly string[] Statements = [];

    private global::System.Collections.Generic.IEnumerable<global::MUnique.OpenMU.Persistence.EntityFramework.Model.GameConfiguration> LoadedGameConfigurations => [];

    private global::System.Threading.Tasks.ValueTask ReadResultAsync(int statementIndex, global::System.Data.Common.DbDataReader reader, global::System.Threading.CancellationToken cancellationToken) => throw new global::System.NotSupportedException();

    private void Fixup()
    {
    }
}
```

The test `GameConfigurationLoaderTests` in `tests/MUnique.OpenMU.Persistence.Initialization.Tests`
compares the object graphs of both loaders. It requires a database, so it's ignored by default.
